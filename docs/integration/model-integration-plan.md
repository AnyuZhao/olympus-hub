# 模型集成实施计划

本文档将 `external-model-install-requirements.md` 中的需求落地为可执行的实施计划，明确模型能力作为增强层接入配置编排底座的步骤。

---

## 1. 前提条件

模型集成必须在以下底座稳定后进行：

1. 配置编排执行器（`planner.rs` + `executor.rs`）已可运行
2. 工具定义模型已支持 `homepage_url`、`install_docs_url`
3. 日志摘要能力（`log_summary.rs`）可提取错误片段
4. 计划校验器（`policy.rs`）已拦截高风险命令

---

## 2. 实施阶段

### Phase 1：模型客户端抽象（2 周）

**目标**：建立不依赖具体厂商的模型调用层，替换当前 Ollama 相关代码。

#### 后端任务
- 新建 `src-tauri/src/core/model_client.rs`
- 定义 `ModelClient` trait，包含以下方法：
  - `generate_install_plan` — 输入：`PlanContext`，输出：`Result<ExecutionPlan, ModelError>`，说明：根据上下文生成工具安装计划
  - `diagnose_failure` — 输入：`DiagnosisContext`，输出：`Result<DiagnosisResult, ModelError>`，说明：分析安装失败日志并给出诊断结果
  - `generate_repair_plan` — 输入：`RepairContext`，输出：`Result<ExecutionPlan, ModelError>`，说明：基于诊断结果生成修复或重试计划
- 实现 `OpenAiCompatibleClient`（支持 OpenAI、Claude、兼容 API）
- 支持结构化 JSON 输出（JSON Schema 约束）
- 统一错误映射：`ModelUnavailable`, `InvalidResponse`, `SchemaMismatch`, `Timeout`

#### 前端任务
- 设置页增加外部模型配置表单：provider / api_base_url / api_key / model_id / timeout
- 增加「测试连接」按钮，调用 `test_model_connection`

#### 测试要求
- Rust：请求体生成正确、非 2xx 响应映射正确、非结构化响应被拒绝、JSON schema 解析失败返回明确错误
- TS：模型配置表单校验、测试连接状态展示

---

### Phase 2：结构化计划 Schema（1 周）

**目标**：定义模型输出与内部计划之间的转换契约。

#### 后端任务
- 在 `plan.rs` 中定义模型输出 schema（与 `data-models.md` 中的 `ExecutionPlan` 对齐）
- 实现 `ModelOutput -> ExecutionPlan` 转换器
- 转换后的计划必须经过现有 `policy.rs` 校验，不通过则拒绝

#### Schema 约束字段说明

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `plan_id` | string | 计划唯一标识 |
| `tool_id` | string | 工具标识 |
| `source_summary` | string | 来源摘要，说明计划生成依据 |
| `risk_level` | enum(low / medium / high / critical) | 风险等级 |
| `human_review_required` | boolean | 是否需要人工审核后才可执行 |
| `install_steps` | 数组（步骤对象） | 安装步骤列表，每项包含 id、name、command、stage、required、timeout_seconds |
| `verification_steps` | 数组（步骤对象） | 安装完成后的验证步骤列表 |
| `rollback_steps` | 数组（步骤对象） | 失败时的回滚步骤列表 |
| `launch_command` | string / null | 工具启动命令，无则为 null |
| `uninstall_steps` | 数组（步骤对象） | 卸载步骤列表 |

#### 测试要求
- Rust：缺少必填字段会拒绝、高风险命令会被 policy 拦截、需要确认的计划不会直接进入执行

---

### Phase 3：安装计划生成接入（2 周）

**目标**：让安装入口可以选择由模型生成计划，再驱动现有安装流程。

#### 后端任务
- 修改 `planner.rs`，在 `generate_install_plan` 中支持双路径：
  - **配置优先路径**：直接从 `ToolOrchestrationConfig` 生成计划（默认）
  - **模型增强路径**：当配置不足以覆盖时，调用 `model_client` 生成草案，再本地校验
- 模型输入上下文包括：工具基础信息、官网 URL、安装文档、环境检测结果、依赖状态
- 模型输出写入 `ExecutionPlan`，再进入现有 `start_install` 流程

#### 前端任务
- 安装页展示「AI 正在生成安装计划」状态（`Planning`）
- 计划就绪后展示 `ExecutionPlanPreview` 组件：步骤列表、风险等级、确认按钮
- 高风险计划展示 `human_review_required` 警告

#### 测试要求
- Rust：正常安装路径可只调用一次计划生成、计划校验失败不会执行命令
- TS：安装页 `Planning` 状态展示、计划预览渲染、确认交互

---

### Phase 4：失败诊断与 React 式重试（2 周）

**目标**：安装失败后，由模型分析日志并给出修复建议或重试计划。

#### 后端任务
- 安装失败时，`planner.rs` 自动或手动触发 `diagnose_failure`
- 诊断输入上下文：
  - `log_summary.rs` 生成的错误片段与尾部摘要
  - 已执行步骤列表
  - 环境检测结果
  - 工具配置上下文
- 模型输出 `DiagnosisResult`，包含：错误分类、根因、建议动作、是否可自动重试、修复计划
- 若 `can_retry_automatically` 为 true 且预算未耗尽，自动生成修复计划并进入重试

#### 前端任务
- 安装失败页展示 `DiagnosisPanel` 组件
- 展示错误分类、根因摘要、建议动作列表
- 若支持自动重试，展示「接受修复建议并重试」按钮
- 展示模型调用预算消耗状态

#### 测试要求
- Rust：安装失败后会触发诊断、超过重试次数后停止自动迭代、预算耗尽后拒绝继续调用
- TS：诊断面板渲染、建议展示、重试按钮交互

---

### Phase 5：预算与审计（1 周）

**目标**：控制调用成本并沉淀审计记录。

#### 后端任务
- 新建 `src-tauri/src/core/budget.rs`
- 支持单任务调用上限（默认 8~10 次，全局上限 20 次）
- 支持全局日预算上限
- 每次模型调用写入审计日志：timestamp / tool_id / plan_id / call_type / tokens_in / tokens_out

#### 前端任务
- 安装页展示剩余调用次数或超限提示
- 设置页展示预算策略与当日消耗

#### 测试要求
- Rust：预算扣减正确、超限拒绝、审计记录完整
- TS：超限提示渲染、预算展示

---

## 3. 调用预算分配

### 正常成功路径

| 阶段 | 调用次数 |
|------|---------|
| 安装计划生成 | 1 次 |
| 可选依赖修正 | 0~1 次 |
| 安装成功总结 | 0~1 次 |
| **小计** | **1~3 次** |

### 失败处理路径

| 阶段 | 调用次数 |
|------|---------|
| 首次失败诊断 | 1 次 |
| 基于摘要生成修复计划 | 1 次 |
| 二次失败后最终建议 | 1 次 |
| **小计** | **额外 2~5 次** |

### 上限策略

- 单次安装任务建议上限：**8~10 次**
- 全局保底上限：**20 次**
- 超限后停止自动迭代，仅展示人工建议

## 4. 安全边界与执行约束

这是模型集成的核心约束，必须优先于功能完整性。

### 4.1 绝对禁止的高风险命令

模型生成的计划中，禁止自动执行下列高风险操作：

- `rm -rf`
- `del /s`
- `format`
- `curl | sh`
- `Invoke-WebRequest | iex`
- 修改注册表高风险项
- 修改系统执行策略
- 静默下载未知二进制并直接执行
- 删除用户目录、系统目录或非工具相关目录

### 4.2 必须本地校验的项目

所有模型输出在执行前必须经过本地校验，包括：

- JSON schema 校验
- 命令白名单 / 黑名单校验
- 工具 ID 与来源校验
- 安装来源可信性校验
- 调用次数与迭代次数校验

### 4.3 模型角色边界定义

模型的角色应定义为：

- **安装计划生成器**
- **日志诊断器**
- **修复建议器**

模型不是：

- 直接系统执行者
- 无限制操作代理
- 不受控的 shell orchestrator

---

## 5. 上线风险与应对

### 风险一：模型输出不稳定

**问题**：同一文档可能在不同调用中给出不同安装策略。

**应对**：
- 使用严格结构化输出
- 引入本地规则校验
- 对高风险来源要求人工确认

### 风险二：日志过长导致调用成本失控

**问题**：原始安装日志可能很长，直接传模型成本高且噪音大。

**应对**：
- 本地先做日志摘要与去噪
- 只传错误附近窗口和关键上下文
- 总是优先传结构化错误摘要，而不是全量日志

### 风险三：工具文档质量参差不齐

**问题**：官网页面可能是营销页，不含真实安装步骤。

**应对**：
- 工具配置中支持单独维护"安装文档正文"
- 优先使用管理员预置安装段落
- 模型提示中强调保守输出与不确定字段留空

### 风险四：外部模型 API 可用性波动

**问题**：配额、速率限制、服务不可用会直接影响安装流程。

**应对**：
- 安装计划应可缓存
- 失败时给出"回退到静态安装配置"的能力
- 明确区分"模型服务失败"和"工具安装失败"

### 风险五：过度自动化导致不可控执行

**问题**：如果让模型自由调用命令，风险不可接受。

**应对**：
- 仅允许模型输出计划，不允许直接执行任意命令
- 本地执行器只运行通过校验的结构化命令集
- 超出约束的计划一律拒绝

---

## 6. 与配置编排优先策略的衔接

```text
默认路径（无模型 / 模型不可用）：
  ToolOrchestrationConfig -> planner -> executor -> 结果

增强路径（模型可用）：
  ToolOrchestrationConfig + 模型生成计划 -> policy 校验 -> executor -> 结果
  
失败路径：
  失败日志 -> log_summary -> model_client diagnose -> 修复计划 -> policy 校验 -> executor -> 结果
```

模型永远是「计划生成器」和「诊断辅助器」，不是执行者。

---

## 7. 验收标准

### 功能验收
- [ ] 管理员可为工具配置官网链接与安装文档
- [ ] 用户点击安装后，系统能生成安装计划（配置或模型）
- [ ] 安装计划通过校验后进入现有安装流程
- [ ] 安装页能展示日志与失败建议
- [ ] 失败后系统可根据日志生成修复建议

### 安全验收
- [ ] 高风险命令不会自动执行
- [ ] 模型返回非结构化内容时流程被拒绝
- [ ] 调用次数超过预算后不再自动迭代

### 工程验收
- [ ] 新增后端实现附带 Rust 测试
- [ ] 模型客户端、计划校验、日志摘要器有单元测试
- [ ] 前端安装页新增状态与展示逻辑有对应测试
