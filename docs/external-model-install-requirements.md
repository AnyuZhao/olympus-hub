# 外部模型驱动安装流程需求文档

> 状态说明：本文档记录的是**未来规划**，不是当前版本已实现能力。
> 当前版本未集成 Ollama、外部托管模型，也不支持基于官方文档或 URL 自动生成工具安装配置。

## 1. 背景与目标

Olympus Hub 当前已经具备以下能力：

- 展示工具列表
- 执行环境检测
- 按配置驱动安装、卸载、启动工具
- 实时记录安装日志并在前端展示
- 支持内置与自定义工具配置

当前新增需求不是继续依赖本地 Ollama，而是切换为**外部托管模型**驱动的安装分析与故障处理流程。

目标是把 Olympus Hub 从“静态配置安装器”升级为“带外部模型决策能力的工具安装助手”，满足以下产品体验：

1. 管理员预先配置工具的官网链接、安装文档、安装来源等信息。
2. 终端用户在工具列表页看到工具并点击“安装”。
3. 系统调用外部模型分析官网文档、安装说明和当前机器上下文，生成可执行安装计划。
4. 系统按安装计划进入既有安装流程并实时展示日志。
5. 若安装失败，系统将错误与日志摘要提交给外部模型进行诊断，并给出下一步建议或修复计划。
6. 在调用预算受限的前提下，整体安装与故障处理流程应尽量控制在**约 20 次模型调用以内**。

---

## 2. 本次需求的重新明确

### 2.1 核心诉求

用户要求的真实目标不是“手动配置所有安装命令”，而是：

- 由产品侧维护每个工具的**官方来源信息**
- 用户点击安装时，由**外部大模型**根据文档与当前上下文进行分析
- 由系统根据模型输出驱动安装流程
- 安装失败时，结合日志继续交给模型做**React 模式**的故障定位与策略调整

### 2.2 非目标

本阶段不把模型直接暴露给用户作为通用聊天入口，不做以下事项：

- 不做通用对话式 AI 助手
- 不允许模型直接无限制执行任意系统命令
- 不做完全无审查的 agent 自主操作系统
- 不依赖本地 Ollama 作为默认方案

---

## 3. 目标用户与角色

### 3.1 管理员 / 产品维护者

负责维护工具元数据，包括：

- 工具名称、描述、分类
- 官网链接
- 官方安装文档 URL 或安装说明正文
- 推荐安装来源
- 可选的预置依赖与约束

### 3.2 终端用户

在桌面端完成如下操作：

- 查看工具列表
- 点击安装
- 查看安装过程
- 查看安装失败时的 AI 建议
- 重试安装或手动执行建议

---

## 4. 目标产品形态

### 4.1 工具配置模式

工具配置分为两层：

1. **产品预置配置**：由产品维护的基础工具元信息
2. **模型运行时生成配置**：用户点击安装后，模型根据文档和上下文生成本次安装计划

也就是说，工具列表不再完全依赖预先写死的 `install_commands`，而是允许以下结构：

- 基础展示信息静态存在
- 具体安装计划由模型在运行时生成或修正

### 4.2 安装入口体验

用户从工具库点击安装后，系统流程应变为：

1. 读取该工具的官网链接、安装文档、已有提示词模板
2. 收集当前机器的基础环境信息
3. 向外部模型发起“安装计划生成”请求
4. 获得结构化安装计划
5. 本地校验后进入既有安装向导执行
6. 将日志流与失败信息反馈给模型，必要时生成新的处理建议

---

## 5. 核心业务流程

### 5.1 安装计划生成阶段

输入：

- 工具基础信息
- 官网 URL
- 安装文档 URL 或正文
- 当前操作系统、架构、磁盘、网络状态
- 已检测到的依赖版本
- 产品预设的安全规则

输出：

- 结构化安装计划，至少包括：
  - 建议安装来源
  - 依赖判断
  - 安装命令列表
  - 卸载命令列表
  - 启动命令
  - 安装后验证命令
  - 风险说明
  - 失败时建议检查项

### 5.2 安装执行阶段

本地执行器负责：

- 顺序执行安装命令
- 写入日志
- 持续更新状态
- 支持取消安装
- 执行安装后验证

此阶段应继续复用当前已有的 Rust 安装执行能力，而不是把执行逻辑迁移给模型。

### 5.3 失败分析阶段

当安装失败时，系统应收集：

- 最新错误信息
- 日志尾部摘要
- 已执行的命令
- 环境检测结果
- 当前工具配置上下文

然后向模型发起“失败诊断”请求，输出：

- 失败根因分类
- 下一步建议
- 是否可以自动重试
- 若允许自动修复，给出新的结构化修复计划

### 5.4 React 模式要求

这里的“React 模式”不是前端框架，而是指**基于执行结果持续反应**的多轮处理模式。

系统要支持：

- 第 1 轮：生成安装计划
- 第 2 轮：执行失败后分析日志
- 第 3 轮：给出修复计划或重试策略

但必须控制总调用预算，避免无限循环。

---

## 6. 模型接入策略

### 6.1 方案选择

推荐采用**外部托管模型 + 结构化输出**方案，而不是自由文本输出。

推荐模型接口能力：

- 支持 JSON Schema 或严格结构化输出
- 支持函数调用 / tool calling，或至少支持可靠 JSON 响应
- 支持单次较长上下文输入

可兼容的模型接入形态：

- OpenAI-compatible API
- Claude structured outputs / tool use API
- 其他支持结构化 JSON 输出的托管模型平台

### 6.2 调用预算

上线目标要求：**单个安装任务的完整模型调用预算约 20 次以内**。

因此推荐采用如下策略：

#### 正常成功路径

1. 安装计划生成：1 次
2. 可选的依赖修正或补充：0~1 次
3. 安装成功总结：0~1 次

成功路径目标控制在 **1~3 次调用**。

#### 失败处理路径

1. 首次失败诊断：1 次
2. 基于摘要日志生成修复计划：1 次
3. 二次失败后的最终建议：1 次

失败路径建议控制在 **额外 2~5 次调用**。

#### 上限策略

- 单次安装任务建议上限：8~10 次
- 全局保底上限：20 次
- 超限后停止自动迭代，只展示人工建议

---

## 7. 结构化输出要求

模型不得直接输出自由文本命令让系统盲执行，而必须返回结构化对象。

### 7.1 安装计划结构

建议至少包含以下字段：

- `plan_id`
- `tool_id`
- `source_summary`
- `dependencies`
- `install_steps`
- `verification_steps`
- `launch_command`
- `uninstall_steps`
- `risk_level`
- `human_review_required`

### 7.2 故障诊断结构

建议至少包含以下字段：

- `error_category`
- `root_cause_summary`
- `confidence`
- `recommended_actions`
- `can_retry_automatically`
- `retry_plan`
- `user_visible_message`

---

## 8. 安全边界与执行约束

这是本需求的核心约束，必须优先于功能完整性。

### 8.1 绝对禁止

模型生成的计划中，禁止自动执行下列高风险操作：

- `rm -rf`
- `del /s`
- `format`
- `curl | sh`
- `Invoke-WebRequest | iex`
- 修改注册表高风险项
- 修改系统执行策略
- 静默下载未知二进制并直接执行
- 删除用户目录、系统目录或非工具相关目录

### 8.2 必须本地校验

所有模型输出在执行前必须经过本地校验，包括：

- JSON schema 校验
- 命令白名单 / 黑名单校验
- 工具 ID 与来源校验
- 安装来源可信性校验
- 调用次数与迭代次数校验

### 8.3 模型角色边界

模型的角色应定义为：

- **安装计划生成器**
- **日志诊断器**
- **修复建议器**

模型不是：

- 直接系统执行者
- 无限制操作代理
- 不受控的 shell orchestrator

应新增或调整的前端能力：

- 展示工具级“官方文档来源”信息
- 安装前展示“AI 正在生成安装计划”状态
- 在安装页展示 AI 风险摘要
- 失败时展示模型生成的修复建议

### 9.2 后端

当前已有关键模块：

- `src-tauri/src/core/config_manager.rs`：工具配置加载

3. 故障诊断 command
4. 模型调用预算控制器

### 9.3 工具配置结构

当前 `Tool` 配置偏静态，未来需要扩展支持：

- 官方文档 URL
- 安装说明正文
- 可选的模型提示模板
- 模型生成策略（如保守/标准）
- 预定义依赖覆盖规则

## 10. 推荐的低调用架构

为了满足约 20 次调用预算，推荐采用以下固定流程，而不是开放式 agent 无限迭代。

### 10.1 安装前

一次请求完成：

- 文档分析
- 安装来源判断
- 依赖识别
- 安装计划生成
- 风险说明生成

### 10.2 安装后失败时

一次请求完成：

- 日志摘要分析
- 根因分类
- 生成修复建议
- 判定是否允许自动重试

### 10.3 自动重试

如允许自动重试，再发起一轮：

- 根据上轮错误生成修正后的安装计划

也就是说，最佳实践是：

- 不把每条命令执行结果都回传模型
- 不做逐行对话式代理循环
- 只在关键阶段调用模型

## 11. 上线约束与风险分析

### 11.1 风险一：模型输出不稳定

问题：

- 同一文档可能在不同调用中给出不同安装策略

应对：

- 使用严格结构化输出
- 引入本地规则校验
- 对高风险来源要求人工确认

### 11.2 风险二：日志过长导致调用成本失控

问题：

- 原始安装日志可能很长，直接传模型成本高且噪音大

应对：

- 本地先做日志摘要与去噪
- 只传错误附近窗口和关键上下文
- 总是优先传结构化错误摘要，而不是全量日志

### 11.3 风险三：工具文档质量参差不齐

问题：

- 官网页面可能是营销页，不含真实安装步骤

应对：

- 工具配置中支持单独维护“安装文档正文”
- 优先使用管理员预置安装段落
- 模型提示中强调保守输出与不确定字段留空

### 11.4 风险四：外部模型 API 可用性波动

问题：

- 配额、速率限制、服务不可用会直接影响安装流程

应对：

- 安装计划应可缓存
- 失败时给出“回退到静态安装配置”的能力
- 明确区分“模型服务失败”和“工具安装失败”

### 11.5 风险五：过度自动化导致不可控执行

问题：

- 如果让模型自由调用命令，风险不可接受

应对：

- 仅允许模型输出计划，不允许直接执行任意命令
- 本地执行器只运行通过校验的结构化命令集
- 超出约束的计划一律拒绝

## 12. 建议的需求拆分

### Phase 1：外部模型接入与安全骨架

- 替换当前 Ollama 相关设置为外部模型配置
- 新增模型客户端抽象层
- 支持结构化安装计划生成
- 加入计划校验器

### Phase 2：工具级文档配置与运行时计划生成

- 工具配置支持官网链接和安装文档
- 点击安装时先生成运行时计划
- 用生成计划驱动现有安装流程

### Phase 3：失败诊断与 React 式重试

- 日志摘要
- 模型故障诊断
- 修复计划生成
- 有上限的自动重试

### Phase 4：预算与运营控制

- 每工具调用计数
- 每次安装任务调用上限
- 模型调用成本与失败率统计

---

## 13. 验收标准

### 13.1 功能验收

- 管理员可以为工具配置官网链接与安装文档
- 用户点击安装后，系统会先生成安装计划
- 安装计划通过校验后进入现有安装流程
- 安装页能展示日志与失败建议
- 失败后系统可以根据日志生成修复建议

### 13.2 安全验收

- 高风险命令不会自动执行
- 模型返回非结构化内容时流程会被拒绝
- 调用次数超过预算后不再自动迭代

### 13.3 工程验收

- 新增后端实现必须附带 Rust 测试
- 模型客户端、计划校验、日志摘要器必须有单元测试
- 前端安装页新增状态与展示逻辑必须有对应测试

---

## 14. 当前推荐决策

基于当前需求，推荐采用以下方案：

1. 使用**外部托管模型**作为默认模型来源
2. 采用**结构化安装计划 + 本地校验 + 本地执行**模式
3. 保留当前 Rust 执行器与日志体系，不把执行权限直接交给模型
4. 将调用流程固定为“安装计划生成 → 安装执行 → 失败诊断 → 可选重试”，避免开放式无限 agent loop
5. 将单任务模型调用预算控制在 8~10 次，整体系统设计上限控制在约 20 次

---

## 15. 下一步实现建议

如果进入实现阶段，建议按以下顺序推进：

1. 先替换设置模型：从 Ollama 配置改为外部模型配置
2. 扩展 `Tool` 配置，支持官网链接和安装文档字段
3. 新增“安装计划生成”后端模块与结构化 schema
4. 把安装入口改成“先生成计划，再执行现有安装流程”
5. 增加失败日志摘要与模型诊断接口
6. 最后补充调用预算控制、重试上限和审计记录
