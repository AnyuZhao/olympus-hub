# 系统架构总览

本文档是 Olympus Hub 的顶层架构文档，明确产品定位、四层架构边界、跨层调用规则、前后端映射及能力底座，作为后端模块拆分与前后端协作的最高依据。

---

## 产品定位与核心能力

### 产品本质

Olympus Hub 表面上是"AI 工具管理器"，但底层具备一个更通用的产品骨架：

> **一个以工具清单为中心，具备环境感知、命令执行、状态管理、日志沉淀和执行计划生成能力的桌面运行平台。**

当前的"AI 工具安装器"只是第一层业务包装，真正可沉淀下来的价值是以下七大可复用核心能力域。

### 七大核心能力域

| # | 能力域 | 所属层 | 状态 |
|---|--------|--------|------|
| 1 | 工具定义与配置管理能力 | 定义层 | 设计中 |
| 2 | 环境感知与依赖检测能力 | 决策层 | 设计中 |
| 3 | 执行计划生成与命令执行能力 | 执行层 | 设计中 |
| 4 | 运行状态管理能力 | 执行层 / 观察层 | 设计中 |
| 5 | 日志采集与回放能力 | 观察层 | 设计中 |
| 6 | 前后端 IPC 与桌面交互能力 | 全层 | 设计中 |
| 7 | 模型驱动决策与计划生成能力 | 决策层 | 设计中 |

---

## 总体分层

```text
定义层 Definition
  ↓ 提供：工具清单（ToolManifest）、平台安装方式（PlatformManifest）
决策层 Decision
  ↓ 提供：执行计划（ExecutionPlan）、故障诊断、修复建议、策略判断
执行层 Execution
  ↓ 提供：命令执行、状态推进、安装验证、重试/取消
观察层 Observation
  提供：日志写入、日志展示、状态展示、审计与摘要
```

---

## 1. 定义层（Definition）

### 职责
- 回答「要安装什么」
- 管理工具清单（ToolManifest），包含检测配置（Detection）、平台级安装方式（PlatformManifest/PackageMethod）、安装方式级依赖（DependencyRef）

### 能力域：工具定义与配置管理

> **把任意可安装工具描述成统一结构化对象，并支持加载、保存、校验和更新。**

配置内容覆盖：工具基础信息（id、name、description、homepage_url、install_docs_url）、版本检测（Detection：check_command + version_regex）、平台安装方式（PlatformManifest → PackageMethod：install_commands / uninstall_commands / installed_check）、安装方式级依赖（DependencyRef：tool_id + min_version）。

该能力的通用性超出 AI 工具场景，可服务：开发者 CLI、本地代理服务、桌面辅助组件，以及任意可用"命令 + 校验 + 依赖"描述的安装对象。

### 包含模块

| 模块 | 输出 |
|------|------|
| `tool_registry` | `Vec<ToolManifest>` |
| `tool_state` | 运行时状态（SQLite） |

### 边界规则
- 工具清单结构**不得依赖特定模型提供方**
- 配置加载器应支持内置配置、用户配置、远程下发等多来源
- 模型只能读取或补充定义层，不能替代它

---

## 2. 决策层（Decision）

### 职责
- 回答「现在应该怎么做」
- 环境分析、执行计划生成、故障诊断、风险评估

### 能力域一：环境感知与依赖检测

> **在执行任务前，收集本机环境事实，并将其转化为可用于决策的结构化上下文。**

采集内容包括：操作系统、CPU 架构、可用磁盘空间、网络连通性、依赖安装状态与版本。

该能力是安装前可行性判断的基础、日志根因定位的上下文来源，以及模型生成执行计划时的重要输入。后续可扩展为支持 PATH 检查、代理与网络模式检测、文件权限检测、进程冲突检测、系统包管理器可用性检测。

### 能力域二：模型驱动决策

> **基于结构化上下文，为本地执行器生成受控计划与修复建议的决策层。**

模型层应负责：文档理解、计划生成、风险说明、错误诊断、修复建议。

模型层不应负责：直接执行系统命令、自由扩展权限边界、绕过本地安全校验。

必须将模型能力单独建模为"决策层"而非嵌入执行层，否则将导致调用次数失控、流程不可预测和安全边界模糊。

### 包含模块

| 模块 | 核心能力 |
|------|----------|
| `environment` | 系统环境检测 |
| `dependency_resolver` | DAG 依赖解析 |
| `planner` | 执行计划生成 |
| `policy` | 安全策略与预算控制 |
| `model_client` | 外部 AI 模型 API 封装 |

### 边界规则
- 模型**不得直接执行系统命令**
- 模型输出必须经过本地 schema 校验和命令黑名单校验
- 单任务模型调用预算上限约 20 次，常规路径控制在 8~10 次

---

## 3. 执行层（Execution）

### 职责
- 回答「把计划真正跑起来」
- 执行通过校验的命令步骤，采集 stdout/stderr，推进状态

### 能力域一：执行计划生成与命令执行

> **按照受控计划执行本地任务，并把执行过程转化为状态变化与日志事件。**

支持：进入安装中状态、顺序执行命令、实时采集 stdout/stderr、取消安装、安装后验证、安装成功或失败收口。

**模型参与后的正确分工**：模型负责生成计划，本地执行器负责执行计划。执行器应保持独立、确定、可校验，不应让模型直接接管。

该能力未来可服务：工具升级、工具修复、启动前准备任务、一次性初始化流程。

### 能力域二：运行状态管理

> **把本地任务的生命周期抽象为统一状态机，并向 UI 和业务流程持续广播。**

运行时状态由三组独立枚举组合表达：

- **install_status**：`NotInstalled` → `Installing` → `Installed` / `Uninstalling` / `Error`
- **runtime_status**：`Stopped` → `Launching` → `Running` / `Exited` / `Error`
- **update_status**：`Unknown` → `Checking` → `UpToDate` / `UpdateAvailable` → `Updating` / `Error`

该能力属于任务执行平台本身，不属于 AI 工具垂类。三组状态枚举分别覆盖安装、运行、更新生命周期，支持前后端状态同步、持久化（SQLite tool_states 表）、运行进程 PID 跟踪。

### 包含模块

| 模块 | 核心能力 |
|------|----------|
| `executor` | 命令执行、取消、stdout/stderr 采集 |
| `updater` | 版本检查、升级触发 |
| `autostart` | 应用级与工具级自启动 |

### 边界规则
- 执行器**只接收结构化计划**，不接受自由文本
- 执行器负责状态推进，但状态定义权在定义层
- 高风险命令（如 `rm -rf`）在执行前已被 policy 拦截

---

## 4. 观察层（Observation）

### 职责
- 回答「发生了什么」
- 日志写入、读取、展示、摘要、审计与回放

### 能力域：日志采集与回放

> **把执行过程沉淀成结构化审计轨迹，并支持实时观察与事后分析。**

支持：写入结构化日志（LogEntry）、按工具持久化、实时事件推送前端、读取最近日志、清理工具日志、错误片段提取、日志摘要生成（LogSummary）。

接入外部模型后，该能力将成为：故障诊断输入、调用预算控制的摘要来源、安全审计依据、用户支持与问题复盘依据。

### 包含模块

| 模块 | 核心能力 |
|------|----------|
| `log_manager` | 日志读写、实时事件推送、日志清理、错误片段提取、摘要生成 |

### 边界规则
- 日志系统必须支持实时观察与事后分析
- 日志摘要必须在本地完成，控制输入模型的 token 长度
- 状态事件必须可被前端和 CLI 同时消费

---

## 跨层调用规则

```text
定义层 ← 被所有层读取
决策层 → 向执行层输出计划
执行层 → 向观察层输出日志事件
执行层 → 向定义层更新状态
观察层 → 向决策层提供诊断输入（日志摘要）
```

### 禁止的调用关系
- 决策层（模型）**不得**直接调用执行层
- 前端 / CLI **不得**直接调用执行层，必须通过 Command 层路由
- 观察层 **不得**反向修改定义层的状态定义

## 与前后端的映射

```text
前端 (React + Tauri IPC)
  ├── 调用 commands → 进入后端
  ├── 监听 events → 来自观察层
  └── 不直接触碰 core

后端 (Rust + Tauri)
  ├── commands —— 参数校验与权限入口
  ├── core —— 四层能力的具体实现
  └── models —— 跨层共享的数据结构

CLI (Rust, 直接链接 core)
  ├── 复用 core 全部四层
  ├── 不依赖前端
  └── 通过 stdout/stderr 呈现观察层输出
```

### 前后端 IPC 与桌面交互

> **在桌面端建立稳定的人机交互层，把后端执行能力映射为可操作、可反馈、可恢复的用户流程。**

前端架构约定：统一通过 API 层调用后端 command，页面层监听事件，store 存储状态，组件负责展示。无论业务是"静态安装"、"模型生成执行计划"还是"日志诊断与修复"，都必须复用这套桌面交互壳。

## 能力底座与收益

### 必须保护的四项能力底座

如果未来要继续演进产品，最不应该被破坏的是：

1. **受控命令执行器** — 独立、确定、可校验，不被模型直接接管
2. **结构化状态机** — 任务生命周期的统一承载，向 UI 和流程持续广播
3. **结构化日志系统** — 审计轨迹、诊断输入、预算控制的基础
4. **统一工具清单模型（ToolManifest）** — 不依赖特定模型提供方，支持多来源加载

模型能力、产品体验和业务策略都应该构建在其上，而不是替代它们。

### 能力抽离的直接收益

**降低产品改造成本**：从"静态安装器"切换到"外部模型驱动安装器"时，底层执行器、日志系统、状态机和 IPC 层全部可以复用。

**降低模型耦合度**：模型只是决策层能力提供方，而不是产品主干。后续更换模型厂商、切换输出 schema、替换调用策略时，不需要推翻安装执行骨架。

**更容易模块化扩展**：后续可继续新增工具升级、工具修复、工具迁移、安装审计、多模型协同能力，而不需要重做整个平台。
