# 配置编排驱动安装需求文档

## 1. 背景

Olympus Hub 前期不引入大模型实时参与安装计划生成，而是优先采用**配置编排驱动安装**的实现路径。

目标是先把平台的定义层、执行层、状态层和日志层做稳定，让工具安装、升级、卸载、自启和失败处理能够通过结构化配置完成。

大模型能力可在后续作为增强层接入，用于生成配置草案或辅助诊断，而不是前期主路径。

---

## 2. 前期目标

前期产品目标：

1. 管理员维护结构化工具配置
2. 用户在工具列表点击安装
3. 系统先做环境与依赖检测
4. 系统按配置编排执行安装流程
5. 系统按配置执行安装后验证
6. 若失败，系统根据配置化规则和日志摘要给出建议
7. 后续支持配置驱动升级、自启和修复

---

## 3. 核心原则

### 3.1 配置先行

所有安装、升级、卸载、修复、自启能力优先由配置描述，而不是由模型实时生成。

### 3.2 本地受控执行

执行器只运行经过本地校验的步骤流，不接受自由文本命令输入。

### 3.3 生命周期完整

前期就要为后续升级、自启、修复预留状态和配置结构。

### 3.4 模型后置

大模型如后续接入，只能作为增强能力：

- 生成配置草案
- 补充失败建议
- 辅助生成升级或修复步骤

不能替代配置编排底座。

---

## 4. 工具配置目标形态

工具定义至少应包含：

- 基础信息
- 官网链接
- 安装文档链接
- 来源类型
- 依赖定义
- 生命周期配置
- 编排流程配置

### 4.1 生命周期配置

生命周期配置应覆盖：

- 是否支持安装
- 是否支持卸载
- 是否支持升级
- 是否支持工具级开机自启
- 默认启动参数
- 自动更新策略

### 4.2 编排流程配置

编排流程至少应支持：

- install flow
- uninstall flow
- upgrade flow
- verify flow
- repair flow（可选）

每个 flow 都由步骤组成。

---

## 5. 编排步骤要求

每个步骤至少应支持以下字段：

- `id`
- `name`
- `stage`
- `command`
- `condition`
- `required`
- `timeout_seconds`
- `retry`
- `on_failure`

步骤能力应支持：

- 条件命中才执行
- 可选步骤失败后继续
- 必需步骤失败后中止
- 步骤级错误建议
- 步骤级日志追踪

---

## 6. 生命周期状态要求

前期建议至少支持以下安装态：

- `NotInstalled`
- `Checking`
- `Installing`
- `Installed`
- `Uninstalling`
- `Upgrading`
- `Repairing`
- `Error`

运行态建议后续单独拆分：

- `Stopped`
- `Launching`
- `Running`
- `LaunchError`

---

## 7. 自动更新要求

自动更新前期不做模型决策，而应基于配置实现：

- 本地版本检查命令
- 远端版本来源
- 更新策略
- 升级 flow

支持：

- 手动检查更新
- 显示 `UpdateAvailable`
- 执行升级 flow
- 升级后验证

---

## 8. 工具级开机自启要求

前期建议采用 `AppManaged` 模式：

```text
系统登录 -> Olympus Hub 启动 -> Olympus Hub 根据工具配置拉起需要自启的工具
```

前期不要求每个工具直接注册系统登录项。

工具级配置应支持：

- `autostart_enabled`
- `autostart_args`
- `autostart_delay_seconds`
- `restart_on_exit`

---

## 9. 失败处理要求

前期失败处理不依赖大模型，应先支持：

- 步骤级失败建议
- 关键错误关键词匹配
- 日志尾部摘要
- 文档链接回跳

也就是说，系统应能在没有模型参与的情况下给出“可执行、可读、可定位”的失败建议。

---

## 10. 与后续大模型能力的衔接

后续若接入大模型，接入方式应是：

1. 模型生成配置草案
2. 本地写入 ToolDefinition / FlowConfig
3. 由配置编排执行器执行

或者：

1. 安装失败后模型生成修复 flow 草案
2. 本地校验后加入 repair flow
3. 再执行修复流程

这样模型永远在配置层或建议层，不直接进入执行层。

---

## 11. 工程验收要求

### 11.1 后端

- 工具配置加载与默认值有 Rust 测试
- 编排步骤解析有 Rust 测试
- 条件判断有 Rust 测试
- 失败建议匹配有 Rust 测试
- 升级与自启策略有 Rust 测试

### 11.2 前端

- 状态展示有测试
- 工具卡按钮逻辑有测试
- 安装步骤展示有测试
- 自启开关与升级入口有测试

### 11.3 验证命令

前期建议验证：

```bash
npm test
npm run build
cargo check
cargo test --lib --no-run
```

---

## 12. 当前推荐结论

前期最佳路线不是“模型驱动安装”，而是：

> **先做配置编排驱动的工具管理平台，再让模型作为后续增强能力接入。**

推荐顺序：

1. 扩展工具定义模型
2. 建立编排步骤模型
3. 改造执行器以支持步骤流
4. 补齐生命周期状态
5. 支持自动更新与工具级自启
6. 增加配置化失败建议与日志摘要
7. 最后再考虑模型生成配置或辅助诊断
