# Olympus Hub 桌面端 UI 设计规范

## Principles

- 交互友好优先于功能堆叠：让用户更快理解当前状态、下一步动作与反馈结果。
- 降低复杂度优先于信息完整：默认只展示当前任务所需信息，技术细节延后暴露。
- 强主次优先于视觉装饰：一级信息、一级动作、一级状态必须先被读到。
- 现代精致建立在克制、稳定、可读、可操作之上，而不是动画或装饰噪音。
- 规范必须可执行：后续代码、测试与评审都必须能够对照本规范判断是否一致。

## 适用范围 (Scope)

本规范仅适用于 Olympus Hub 当前桌面端主应用的前端界面与交互实现。

当前强制受本规范约束的对象包括：

- `src/components/Layout.tsx` 定义的应用壳层与导航结构
- `src/pages/ToolListPage.tsx` 对应的工具库首页
- `src/components/ToolCard.tsx`、`src/components/StatusBadge.tsx` 等首页核心组件
- `src/pages/SettingsPage.tsx` 对应的设置页与其表单交互
- `src/pages/InstallWizardPage.tsx`、`src/components/PreCheckPanel.tsx`、`src/components/LogViewer.tsx` 对应的安装向导与长任务反馈体验

本规范同样约束以下输出：

- 后续新增页面必须先归类到本规范定义的页面模板类型后再设计与实现
- 后续新增组件必须遵循本规范定义的组件层级、交互优先级与状态反馈规则
- 后续前端代码、测试和评审结论都应以本规范为依据判断一致性

## 非目标

以下内容不属于本规范当前范围：

- 移动端界面规范
- 品牌视觉系统、营销站、官网或宣传页设计
- 脱离当前产品信息架构的全新导航重构
- 当前会话内直接改写生产前端代码以追求完全视觉对齐
- 与 UI 规范无关的业务流程重构、后端重构或工具安装逻辑改造
- 一次性全量重写所有页面和组件

## 边界说明

- 本规范优先服务当前桌面端主应用，而不是未来所有可能的产品形态。
- 本规范以当前代码基线为出发点，要求在现有深色桌面工具风格上演进，而不是推翻重做。
- 若未来要扩展到更多页面或更多平台，应在本规范基础上追加新章节，而不是改写当前核心边界。

## 现有视觉语言基线

### 当前已落地的视觉基础

当前代码已经形成一套稳定的深色桌面工具视觉基线，后续设计必须在此基础上演进：

- `src/components/Layout.tsx` 定义了固定左侧导航 + 主内容区的桌面壳层，使用 `bg-surface` 和 `bg-surface-card` 建立主背景与次级容器的层次。
- `src/components/ToolCard.tsx` 使用卡片容器、低透明边框、圆角和强调色 hover 来构成首页的主要视觉单元。
- `src/pages/SettingsPage.tsx` 延续相同的卡片容器与表单控件风格，说明当前产品已经具备统一的页面容器语言。
- `tailwind.config.js` 中的 `surface` 与 `accent` 主题色提供了当前视觉系统的核心基础：深色背景、卡片色层、亮蓝强调色。

### 现代精致的执行性定义

本项目中的“现代精致”不是高装饰、高噪音或高动效，而是以下可执行规则的组合：

1. **层次先于装饰**
   - 通过背景层、文字权重、间距和容器分组建立主次，而不是依赖大量阴影和装饰元素。
   - 一级信息必须先被读到，再出现二级信息和补充信息。

2. **深色基底 + 克制强调色**
   - 深色背景仍然是当前桌面端的主基调。
   - `accent` 只用于主操作、选中态、关键强调，不应扩散为大面积装饰色。

3. **卡片作为主要信息容器**
   - 卡片承担模块分组和操作承载，不应被做成复杂的视觉插画或超高信息密度面板。
   - 卡片之间依靠间距、边框和轻微 hover 差异区分，而不是强烈阴影竞争。

4. **文字层级清晰且数量受控**
   - 标题、状态、主操作是一级视觉焦点。
   - 分类、描述、辅助提示属于二级或三级信息。
   - 单一视图中同时竞争注意力的文本层级不能过多。

5. **动效轻、短、稳**
   - 当前实现中的 `transition-colors`、轻 hover 与少量 pulse 已经说明产品适合克制动效。
   - 后续规范默认不使用大幅位移、复杂弹跳、持续闪烁等炫技动画。

6. **工程工具感保留，但表达更干净**
   - `LogViewer` 这类黑底终端风格反馈反映了当前产品的工程属性，应保留可信度。
   - 但后续应通过信息层级、间距和容器关系降低“工程噪音”直接占据主视线的问题。

### 当前需要保留的视觉优点

- 固定侧边栏与主内容区的桌面结构清晰，适合继续使用。
- 深色背景 + 卡片层的组织方式已经具备现代桌面工具的基础气质。
- 强调色只在选中态和主按钮中出现，当前克制程度是合理的。
- 状态颜色映射（灰/黄/绿/蓝/红）已经形成可延展的状态语言基础。

### 后续需要升级但当前不直接改代码的方向

- 工具卡片中信息和动作竞争仍然偏多，需要进一步强化一级/二级/三级层级。
- 设置页虽然视觉统一，但“即时生效”方向尚未落地，后续需要让视觉反馈与交互模型一致。
- 安装向导中的日志反馈当前偏工程终端风格，后续需控制其在页面中的视觉优先级。
- 当前容器、文字与按钮已具备基础语言，但还没有被正式提炼成 token 与组件规则。

## 现有交互与状态基线

### 当前交互模式总览

当前桌面端交互主要围绕三类页面模式展开：

- **工具库模式**：`src/pages/ToolListPage.tsx` 负责加载工具列表、订阅状态变更，并把核心交互委托给卡片组件。
- **表单设置模式**：`src/pages/SettingsPage.tsx` 负责目录选择、开机自启开关和显式保存反馈。
- **流程向导模式**：`src/pages/InstallWizardPage.tsx` 负责环境检测、安装执行、日志反馈、失败恢复和流程切换。

这些页面已经形成了当前产品的真实交互基线，后续规范应在此基础上整理和收紧，而不是重写为完全不同的交互模型。

### 当前状态类型与表现基线

当前代码已经明确存在并可观察的状态包括：

- **loading**：工具库首次加载、安装详情检测中、保存中、安装中
- **empty**：工具库无工具配置、日志区无日志输出
- **error**：工具状态异常、安装失败、安装详情缺失时的兜底错误页
- **success**：设置保存成功、安装完成成功
- **disabled**：忙碌中按钮禁用、环境不满足时禁用继续安装
- **destructive**：卸载动作需要显式确认，并使用红色危险风格
- **busy / long-running**：安装中、启动中、长日志持续输出

### 保留的当前模式

以下模式符合当前产品方向，应保留为未来规范的基线：

1. **状态驱动的动作可见性**
   - `ToolCard` 当前根据状态决定显示“安装 / 启动 / 卸载 / 处理中 / 运行中”，这是一种清晰的动作约束方式，应保留。

2. **页内主流程反馈优先**
   - 安装向导当前将成功、失败、建议下一步、日志等信息集中在页面内容区，而不是全部依赖浮层提示，这种模式适合桌面工具场景，应保留。

3. **危险操作显式确认**
   - `ToolCard` 中卸载前使用确认对话，这是当前最基础的防误触策略，应作为后续危险操作规则的起点。

4. **长任务使用专门区域承载**
   - `InstallWizardPage` 中安装日志使用独立 `LogViewer` 容器承载，而不是混入普通文本区域，这个模式应保留。

### 需要优化的当前模式

以下模式当前可用，但与既定设计方向存在偏差，需要在后续规范中收紧：

1. **工具卡片动作竞争**
   - 当前卡片可能同时出现主动作、危险动作与状态提示，容易削弱“单主操作”和“强主次”的方向。

2. **设置页交互仍偏显式保存**
   - 当前 `SettingsPage` 是“修改 → 点击保存 → 显示已保存”，这与“即时生效”方向不一致，需要重新定义哪些设置即时生效、哪些仍需确认。

3. **日志反馈优先级过高**
   - `LogViewer` 当前是强工程终端感的黑底大块容器，在流程页面中容易和主操作竞争注意力，后续需定义其层级边界。

4. **空状态与错误状态语言尚未统一**
   - 工具库、日志区、安装详情缺失页虽然都有兜底，但表达形式和语气还未形成统一规范。

### 明确禁止的未来模式

后续规范应明确禁止以下交互模式：

1. **把多个动作都做成同等主按钮**
   - 同一卡片或同一流程区块内，不允许多个动作争夺主视觉权重。

2. **仅靠 Toast 承载关键错误**
   - 阻断性错误、流程失败、恢复建议等不能只通过 Toast 传达，必须保留页内可见反馈。

3. **让长日志直接成为页面第一视觉焦点**
   - 日志应服务流程，不应压过主任务标题、状态和下一步动作。

4. **让危险操作缺少确认或弱化标识**
   - 卸载、清除、覆盖等动作不能伪装成普通次级按钮。

### 交互基线总结

当前交互基线可概括为：

- 业务动作已经基本由状态驱动，结构清晰；
- 页内反馈优先于浮层反馈，适合桌面工具产品；
- 但主次层级、即时生效策略、状态矩阵和危险动作规则还没有被正式文档化；
- 后续规范的重点不是发明新交互，而是把现有模式收敛成统一规则。

## Token 架构 (Tokens)

### Token 分层原则

本规范采用三层 Token 架构：**primitive token → semantic token → component token**。

- **primitive token**：最基础、不可再拆分的视觉原子值，例如颜色值、字号、间距、圆角、阴影、动效时长。
- **semantic token**：面向界面语义的命名层，例如页面背景、卡片背景、主文本、次文本、危险操作、主按钮、边框层级。
- **component token**：面向具体组件的派生规则，例如工具卡片容器、侧边栏导航项、设置表单输入框、状态标签、日志容器。

三层之间的关系必须固定为：

- primitive token 提供视觉原料；
- semantic token 负责把视觉原料翻译成界面语义；
- component token 只能消费 semantic token，而不应直接散落硬编码值。

### 当前必须覆盖的 Token 类别

本项目当前必须定义的 Token 至少包括：

- **颜色**：背景、卡片、hover、强调、成功、警告、错误、边框、主文本、次文本、弱文本
- **排版**：字号、字重、行高、标题层级、正文层级、辅助说明层级
- **间距**：页面外边距、卡片内边距、区块间距、控件间距、列表/栅格间距
- **圆角**：页面内卡片、按钮、输入框、标签、日志容器的统一圆角层级
- **阴影与边框**：边框透明度、卡片 hover 强度、层级分隔方式
- **动效**：hover、状态切换、轻反馈的时长和节奏
- **尺寸与密度**：按钮高度、输入框高度、卡片最小高度、导航宽度、日志区最大高度
- **层级**：z-index 与浮层优先级规则

### 当前代码中的 primitive token 基线

从 `tailwind.config.js` 可直接提取的当前 primitive token 基线包括：

- `surface.DEFAULT = #1a1a2e`
- `surface.card = #16213e`
- `surface.hover = #1f2d4a`
- `accent.DEFAULT = #4f8ef7`
- `accent.hover = #6aa3ff`

这些 token 已经构成当前深色桌面工具语言的最小颜色基线，后续不应跳过这层直接发明新的组件颜色规则。

### semantic token 定义方向

基于当前实现，semantic token 至少应形成如下语义层：

- **surface/page**：整页主背景
- **surface/card**：卡片与表单容器背景
- **surface/interactive-hover**：导航项、卡片、按钮 hover 背景
- **text/primary**：主标题与核心信息
- **text/secondary**：辅助标题、分类、说明
- **text/muted**：弱说明、占位提示、空状态辅助文案
- **action/primary**：主操作按钮与选中态强调
- **action/danger**：危险操作按钮与错误强调
- **feedback/success**、`feedback/warning`、`feedback/error`
- **border/subtle**：弱边框与分隔线

### component token 定义方向

在当前主应用中，component token 至少应覆盖：

- `sidebar.nav.item`
- `sidebar.nav.item.active`
- `tool-card.container`
- `tool-card.title`
- `tool-card.meta`
- `tool-card.primary-action`
- `tool-card.destructive-action`
- `settings.section.container`
- `settings.input`
- `settings.switch`
- `status-badge.*`
- `log-viewer.container`

### 与 Tailwind / utility class 的映射规则

本项目当前实现依赖 Tailwind utility class，因此 Token 架构必须映射到 Tailwind，而不是绕开它：

1. 颜色和核心尺寸优先落到 `tailwind.config.js` 的 theme 扩展中。
2. 组件实现中优先消费语义化 class 组合，而不是重复堆叠分散的硬编码颜色值。
3. 文档允许当前阶段继续使用 utility class，但后续实现必须能说明这些 utility 对应了哪一层 token。
4. 不允许在未来实现中随意引入新的孤立十六进制颜色，除非先补入 token 体系。

### 当前必须保留与未来可扩展的边界

- **当前必须落地**：dark-first 桌面主应用所需的颜色、排版、间距、圆角、状态、动作、容器 token。
- **当前仅预留扩展**：双主题（light/dark）支持、品牌插画色系、营销页面专用 token、移动端密度 token。

### Token 架构目标

Token 架构的目标不是做一套抽象词典，而是为后续页面模板、组件规范和差距分析提供统一的视觉语言底座。

## 工具卡片信息层级规则

### 卡片角色定义

工具卡片是 Olympus Hub 首页中的**一级信息容器**，职责是帮助用户快速完成“识别工具状态 → 理解当前可做的主动作 → 决定是否进入安装/启动/卸载流程”。

因此，卡片不能承担完整详情页职责，也不能塞入过多并列信息。卡片的目标是**快速扫描 + 明确主动作**，而不是展开所有背景信息。

### primary info

以下信息属于卡片中的一级信息，必须优先被看见：

1. **工具名称**
   - 始终位于卡片左上区域，使用最高文字权重。
2. **当前状态**
   - 由 `StatusBadge` 承担，位于标题区同层，用于第一时间说明工具当前所处状态。
3. **primary CTA**
   - 卡片底部只允许一个主动作，必须和当前状态强关联。

### secondary info

以下信息属于二级信息，应在一级信息之后被感知：

- 工具分类
- 工具描述摘要
- 当前运行 PID（仅在运行态出现）
- 错误摘要（仅在异常态出现）

二级信息的职责是帮助用户理解上下文，但不得抢占主操作与状态信息的优先级。

### hidden by default

以下信息不应默认出现在卡片中，应隐藏到详情页、安装向导或未来扩展层中：

- 依赖列表与版本要求
- 安装命令全文
- 卸载命令全文
- 启动参数详情
- 长错误堆栈或长日志
- 工具来源、校验信息、技术细节元数据

### 信息密度规则

- 每张卡片默认只承载 1 个任务对象，不做多层嵌套。
- 描述文本应限制在简短摘要层，当前两行截断方向是合理基线。
- 同一张卡片中同时高亮的信息层级不应超过三层：标题/状态、摘要、操作。
- 卡片内不应出现多个需要用户同时权衡的主视觉区域。

### 操作区规则

- **每张卡片仅允许一个 primary CTA**。
- 当前 primary CTA 可根据状态在“安装”或“启动”之间切换。
- 卸载始终视为危险动作，只能作为降级动作出现，不能与 primary CTA 竞争视觉权重。
- 忙碌态下，主操作必须让位于“处理中”占位，避免用户重复触发。

### 当前基线中应保留的部分

- `ToolCard` 现在已经具备标题、状态、摘要、底部操作区的基础分层，这一结构应保留。
- 当前通过状态切换操作按钮的方式是正确方向，应继续作为卡片动作模型基线。
- 错误信息和运行 PID 以条件形式补充显示，属于合理的按需暴露模式。

### 当前需要优化的部分

- 当前卡片底部可能同时出现主动作、危险动作和状态文本，容易削弱“单主操作”原则。
- 分类、描述、错误提示、PID 与按钮区域之间的视觉优先级尚不够严格，需要后续在组件规范中进一步收紧。
- 卸载虽然已是危险色，但当前仍与主操作同处一层操作区，后续可通过位置与密度控制进一步弱化其竞争性。

### 明确禁止的未来模式

- 禁止把卡片扩展为完整详情面板。
- 禁止在同一卡片内并列两个同级 primary CTA。
- 禁止让技术细节（依赖、命令、长错误）默认暴露在首页卡片中。
- 禁止为了“信息完整”牺牲卡片可扫描性。

## 单主操作与危险操作规则

### 主操作的层级边界

本规范中的 primary action 必须按层级理解，不允许跨层混淆：

- **page-level primary action**：页面级最重要动作，用于驱动当前页面的主任务，例如安装向导中的“继续安装”。
- **section-level primary action**：某个局部区块中的主动作，仅在页面中存在多个功能区块时使用。
- **card-level primary action**：卡片内部唯一主动作，用于从列表态进入下一步流程。

任何时候都不允许让不同层级的 primary action 在同一视觉层内互相竞争。

### page-level 规则

- 每个页面同一主任务区域只允许一个 page-level primary action。
- page-level primary action 必须与页面标题、页面目标和当前状态强绑定。
- 阻断性流程页（如安装向导）应优先采用 page-level primary action，而不是让用户在多个动作间自行判断主次。

### section-level 规则

- section-level primary action 仅在页面存在多个相对独立功能区块时允许出现。
- section-level action 不能视觉上压过 page-level primary action。
- 设置页中的局部控件操作（如浏览目录）属于辅助 action，不应升级为区块主动作。

### card-level 规则

- 每张卡片仅允许一个 card-level primary action。
- card-level primary action 当前只能承担“安装”或“启动”这类顺着工具状态推进的动作。
- card-level primary action 的存在是为了减少判断成本，不允许在同一卡片中再引入第二个同级主按钮。

### 危险操作规则

危险操作包括但不限于：卸载、清除、覆盖、不可逆删除、会导致状态回退的操作。

这些操作必须遵循以下统一规则：

1. **视觉降级**
   - 危险操作不能与 primary action 共用同等级强调色。
   - 危险操作应使用 danger 语义色，并弱于主按钮的视觉权重。

2. **确认机制**
   - 危险操作必须有确认步骤。
   - 当前 `ToolCard` 中卸载前使用确认对话是合理基线，应保留并进一步规范。

3. **位置规则**
   - 危险操作应放在主操作之后，且不占据卡片或页面中的主要视觉位置。
   - 危险操作不应与 page-level primary action 紧邻到造成误触风险。

4. **状态约束**
   - 忙碌态下不应允许危险操作继续被触发。
   - 危险操作若会影响长任务过程，应优先通过显式状态和确认中断，而不是静默执行。

### 当前应保留的模式

- `InstallWizardPage` 中“继续安装”作为 page-level primary action 的模式应保留。
- `ToolCard` 中通过状态驱动 primary action 在“安装 / 启动”间切换的模式应保留。
- `ToolCard` 中卸载使用危险色并带确认对话的模式应保留为危险操作基线。

### 当前需要优化的模式

- 当前 `ToolCard` 中主动作与危险动作仍处于同一操作区块，后续需通过位置、间距与密度规则进一步拉开层级。
- 当前设置页主要依靠“保存设置”作为 page-level primary action，但未来若转向即时生效，需要重新界定页面主动作是否继续存在。

### 明确禁止的未来模式

- 禁止在同一卡片或同一区块中并列两个同级 primary CTA。
- 禁止危险操作看起来像普通辅助按钮。
- 禁止省略危险操作确认步骤。
- 禁止让用户在同一屏首要区域同时看到多个互相竞争的主动作。

## 状态与反馈矩阵 (State/Feedback)

### 总体原则

Olympus Hub 当前桌面端应采用 **页内反馈优先，Toast 作为轻量补充，Modal 仅用于阻断性确认** 的反馈策略。

- **inline** 用于与当前页面主流程强相关、用户必须看到并理解的信息。
- **toast** 只用于轻量、短暂、不阻断流程的结果反馈。
- **modal** 仅用于高风险确认、不可逆操作确认或必须中断当前任务让用户做决定的场景。

### 状态矩阵

#### loading
- 适用场景：工具库首次加载、安装详情检测中、设置保存中。
- 反馈形式：优先使用 **inline** 页面内加载态。
- 规则：loading 信息必须出现在用户当前任务区域，而不是只通过 toast 告知。

#### success
- 适用场景：设置保存成功、安装成功、重载详情成功。
- 反馈形式：以 **inline** 为主，可补充轻量 **toast**。
- 规则：若成功结果改变了当前页面状态，应优先让页面本身可见变化，而不是只给 toast。

#### warning
- 适用场景：环境存在风险项、推荐但非必须依赖缺失、即将执行危险动作前的次级提醒。
- 反馈形式：优先使用 **inline** 提示条或页内说明。
- 规则：warning 不应伪装成 success，也不应直接中断流程。

#### error
- 适用场景：安装失败、安装详情缺失、启动失败、设置保存失败。
- 反馈形式：必须使用 **inline** 页内错误反馈；必要时可追加 toast，但不能只靠 toast。
- 规则：error 需要同时告诉用户发生了什么、影响什么、下一步可以怎么做。

#### empty
- 适用场景：工具列表为空、日志列表为空、某区域暂无内容。
- 反馈形式：使用 **inline** 空状态占位。
- 规则：empty 状态应说明“当前没有什么”和“用户接下来能做什么”。

#### disabled
- 适用场景：环境不满足时禁用继续安装、忙碌态下禁用按钮。
- 反馈形式：组件自身禁用样式 + 邻近上下文说明。
- 规则：禁用不能无解释，必须通过页内文案或状态说明告诉用户为什么当前不能操作。

#### busy
- 适用场景：安装中、启动中、长任务执行中。
- 反馈形式：使用 **inline** 忙碌状态和专门的任务反馈区域（如日志容器）。
- 规则：busy 态下必须抑制重复触发，并保持任务进度/日志可追踪。

#### destructive
- 适用场景：卸载、清除、覆盖、会导致状态回退的动作。
- 反馈形式：触发前使用 **modal** 或确认机制，执行后使用 **inline** 结果反馈。
- 规则：destructive 不能只给轻提示，确认必须发生在动作执行前。

### inline / toast / modal 的边界

#### inline 必须承载的内容
- 主流程状态变化
- 阻断性错误
- 长任务进度与结果
- 环境检测结果
- 空状态说明

#### toast 允许承载的内容
- 设置已保存
- 操作已触发且不会让用户失去上下文
- 非关键成功反馈的轻量提示

#### toast 明确禁止承载的内容
- 阻断性错误
- 危险操作确认
- 用户必须阅读后才能继续的关键信息
- 长任务的唯一反馈来源

### 当前应保留的模式

- `InstallWizardPage` 中把成功/失败/建议下一步放在页内，是正确基线。
- `SettingsPage` 当前“已保存”轻反馈可以作为 future toast/inline 组合的起点。
- `LogViewer` 作为长任务反馈专门区域的模式应保留。

### 当前需要优化的模式

- 当前设置页成功反馈仍偏单点文案，未来需要统一为规则化的 inline + toast 组合。
- 当前空状态、错误状态和警告状态虽然存在，但尚未形成统一语气和层级标准。
- 当前安装流程中的日志区域已经承担了大量反馈职责，后续需进一步限制其视觉优先级。

### 明确禁止的未来模式

- toast 不得用于阻断性或高风险确认信息。
- 禁止只在 console 中记录错误而页面无反馈。
- 禁止让 empty、warning、error 共用模糊表达方式。
- 禁止让长任务在没有 inline 状态区的前提下只依赖日志或 toast。

## 页面模板规范 (Page Templates)

本规范按页面类型而不是按具体页面名称定义模板。未来新增页面必须先归类到下列模板之一，再决定布局和组件组合。

### dashboard/list 模板

适用对象：工具库首页、未来的资源列表页、可扫描型概览页。

#### layout
- 顶部应包含页面标题区。
- 标题区之后是筛选、刷新或辅助操作区。
- 主内容区以卡片栅格或列表承载多个对象。

#### hierarchy
- 页面标题与主说明为一级信息。
- 列表/卡片集合是页面主任务区。
- 次级说明、筛选说明、弱提示信息属于二级层。

#### actions
- 页面级最多一个主动作；工具库当前场景可无 page-level primary action。
- 单个卡片内部遵循 card-level primary action 规则。

#### feedback
- 加载、空状态、局部错误都优先在主内容区内反馈。
- 刷新结果可使用轻量 toast，但列表主状态必须页内可见。

#### states
- 必须覆盖 loading、empty、error、busy、success（如适用）。

#### desktop constraints
- 列表区应适配宽屏与窄窗，不得因窗口缩小导致卡片不可读。
- 滚动应发生在内容区，不影响固定导航结构。

### settings/form 模板

适用对象：设置页、偏表单的配置页。

#### layout
- 顶部为标题区与简短说明。
- 中部为按主题分组的表单区块。
- 底部可有保存反馈区或局部状态区。

#### hierarchy
- 分组标题先于具体控件。
- 表单控件优先级高于辅助说明，但说明必须足够支持理解和避免误操作。

#### actions
- 即时生效是目标方向，但若当前实现仍有 page-level primary action，应明确其只是过渡模式。
- 浏览、清空、恢复默认等属于辅助操作，不得升级为页面主动作。

#### feedback
- 保存成功、失败、回滚和风险提示都应在表单上下文内反馈。
- toast 只能作为补充，不替代表单上下文反馈。

#### states
- 必须覆盖 idle、saving、success、error、disabled。

#### desktop constraints
- 表单宽度应控制在可阅读范围内，避免超宽导致扫描困难。
- 切换和输入控件要保证桌面鼠标与键盘都可稳定操作。

### wizard/install 模板

适用对象：安装向导、分步骤执行流程页、长任务流程页。

#### layout
- 顶部包含返回、标题和当前任务识别信息。
- 主内容区随步骤切换展示检测、执行、完成等不同阶段内容。
- 日志或长任务反馈区是主内容的子区块，不应独立成为页面主标题替代物。

#### hierarchy
- 当前步骤状态是一级信息。
- 主动作（继续安装 / 重试 / 返回）紧随步骤内容出现。
- 日志是支撑区，不应压过任务状态与动作。

#### actions
- 每一步只能有一个明确 page-level primary action。
- 取消、返回、重试等动作属于次级或恢复性动作。

#### feedback
- 环境检测结果、失败原因、建议下一步都必须页内可见。
- 长任务日志作为补充反馈容器，不替代状态结论。

#### states
- 必须覆盖 checking、precheck、installing、done、missing-precheck-data、failed、cancelled（如适用）。

#### desktop constraints
- 长日志区需有独立滚动区域。
- 长任务过程中页面结构不能频繁跳动，避免用户失去上下文。

### detail/log-heavy 模板

适用对象：日志详情页、诊断详情页、未来的重内容技术详情页。

#### layout
- 顶部仍需保留页面标题和任务上下文。
- 中下部可以引入大块可滚动内容容器。

#### hierarchy
- 标题与摘要结论必须先于技术内容。
- 详细日志、技术明细、原始输出属于次级阅读区。

#### actions
- 页面主动作通常较少，以复制、导出、返回、重新执行等辅助动作为主。

#### feedback
- 若存在错误，应先展示总结，再允许查看详细内容。

#### states
- 必须覆盖 empty、error、loaded、copy-success 等适用状态。

#### desktop constraints
- 长内容必须有良好的滚动、折行与容器高度约束。
- 不应让技术内容挤压基础导航和返回能力。

### 页面模板总规则

- 所有页面模板都必须显式定义 `layout / hierarchy / actions / feedback / states / desktop constraints` 六类字段。
- 不允许为了追求统一，把所有页面强行压成同一骨架。
- 不存在的页面类型不应凭空发明为当前必须模板。

## 组件规范 (Components)

### 导航项

#### 允许行为
- 导航项必须清晰表达当前所在页面与可切换目标。
- 选中态应同时通过颜色与背景层表达，而不是只依赖单一颜色变化。
- 导航项应保持轻量，优先服务页面切换，不承载复杂操作。

#### 禁止行为
- 禁止把危险操作放进主导航项。
- 禁止用过重装饰让导航压过主内容。

### 工具卡片

#### 允许行为
- 作为首页一级信息容器，承载标题、状态、摘要与唯一主动作。
- 根据工具状态切换主动作。
- 在需要时以降级方式补充错误摘要或运行 PID。

#### 禁止行为
- 禁止承载完整依赖详情、安装命令全文或长错误文本。
- 禁止并列多个同级主按钮。

### 状态标签

#### 允许行为
- 统一承载工具状态的颜色与标签映射。
- 使用简短、高识别度文本表达状态。

#### 禁止行为
- 禁止把状态标签做成可点击主操作。
- 禁止同一状态在不同页面使用互相冲突的颜色语义。

### 日志容器

#### 允许行为
- 作为长任务反馈的专门区域存在。
- 支持独立滚动、时间戳、阶段标识和消息正文。

#### 禁止行为
- 禁止日志容器成为页面第一视觉焦点。
- 禁止日志替代状态结论或主动作说明。

### 表单项

#### 允许行为
- 输入框、选择器、开关等必须有明确标签与辅助说明。
- 表单项应和所属区块的目的保持一致。

#### 禁止行为
- 禁止无标签控件直接出现在设置页中。
- 禁止把辅助说明写得比控件本身更抢眼。

### 区块容器

#### 允许行为
- 用于组织表单区、反馈区、日志区和说明区。
- 通过背景、边框、间距而不是复杂装饰建立分组。

#### 禁止行为
- 禁止为每个区块引入完全不同的视觉语言。
- 禁止区块之间缺乏统一间距与层级。

### 空状态

#### 允许行为
- 明确说明当前没有什么内容。
- 给出用户下一步可以做什么或至少说明当前上下文。

#### 禁止行为
- 禁止只写模糊一句话而没有语义上下文。
- 禁止用空白代替空状态。

### Toast

#### 允许行为
- 承担轻量成功反馈、非阻断提醒、局部完成提示。
- 保持短、轻、快，不干扰主流程。

#### 禁止行为
- 禁止承载阻断性错误、危险确认或必须阅读后才能继续的信息。
- 禁止作为页面主反馈的唯一来源。

### 危险确认

#### 允许行为
- 用于卸载、清除、覆盖等危险动作的确认。
- 必须先确认，再执行。

#### 禁止行为
- 禁止省略确认步骤。
- 禁止把危险确认做成轻量 toast 提示。

### 组件级总规则

- 所有关键组件都必须同时定义允许行为与禁止行为。
- 组件规则必须从 token、交互矩阵和页面模板中继承，而不是各自为政。
- 组件不能越权承担不属于自己层级的职责，例如让状态标签兼任主按钮、让日志容器兼任错误总结。

## 桌面端专属约束 (Desktop Constraints)

### window size

- 桌面端必须以固定应用壳层为前提，窗口缩放不能破坏左侧导航 + 主内容区的基本结构。
- 最小窗口尺寸必须以保证导航、主内容标题和主操作仍可读为底线。
- 窄窗情况下，优先压缩内容密度，而不是让核心操作或标题被截断到不可用。

### scroll regions

- 滚动应优先限制在主内容区内，不影响固定导航的稳定性。
- 长日志、长表单、长列表应拥有明确且独立的滚动区域。
- 页面中不应出现多个无边界竞争的滚动容器，否则会破坏桌面端的操作稳定性。

### long-running tasks

- 长任务必须有持续可见的页内状态反馈。
- 安装、启动、检测这类过程不应只靠 toast 提示，而必须在主内容区内保留状态与进度上下文。
- 长任务期间页面结构应尽量稳定，避免任务区因状态切换发生剧烈跳动。

### keyboard/mouse

- 桌面端交互默认支持鼠标与键盘双输入，而不是只为鼠标点击设计。
- 可聚焦控件必须保持明确的焦点可见性。
- 需要快速往返的流程（例如返回、重试、确认）应在结构上支持键盘可达性。

### density

- 桌面端允许比移动端更高的信息密度，但必须服从强主次原则。
- 首页卡片、设置表单和安装向导的密度不能互相污染：
  - 工具库偏扫描效率
  - 设置页偏清晰输入
  - 安装向导偏流程感与反馈稳定性

### current baseline mapping

- `Layout.tsx` 当前固定左侧导航 + 主内容区模式，是桌面专属结构基线。
- `InstallWizardPage.tsx` 中的长日志容器说明当前已存在独立滚动区与长任务反馈需求。
- `ToolListPage.tsx` 和 `ToolCard.tsx` 说明当前内容密度以卡片扫描为主，而不是长表格或多列数据密集布局。

### mobile out-of-scope reminder

- mobile 属于 out-of-scope，本节只定义桌面端约束，不为移动端布局、触屏密度或移动交互模式提供规范。

### 明确禁止的未来模式

- 禁止把响应式 Web 断点逻辑直接照搬成桌面规范结论。
- 禁止让导航与主内容同时滚动造成定位丢失。
- 禁止长日志或长列表没有独立滚动区。
- 禁止只按鼠标点击路径设计关键交互，而忽略键盘可达性。

## 可访问性最低要求

本规范中的可访问性要求是**必须项**，不是建议项。桌面端允许高密度信息，但不能以牺牲基本可达性为代价。

### keyboard

- 所有关键交互必须支持键盘可达。
- 页面级主动作、主要输入控件、导航项、确认与返回操作都必须能通过键盘访问。
- 未来实现不得把核心流程设计成只能依赖鼠标点击完成。

### focus

- 可聚焦控件必须保持明确的 focus visible 表达。
- 焦点状态不能只依赖极弱颜色变化，必须在深色背景下清晰可见。
- 焦点流向应与页面主任务顺序一致，不得出现明显跳跃或迷失上下文。

### target size

- 交互目标必须具备稳定点击区域，按钮、切换开关、导航项不能过小。
- 即使在高密度布局中，也不能为了压缩界面而把点击区域缩减到难以命中的程度。

### contrast

- 主文本、次文本、状态标签、输入控件与背景之间必须维持清晰对比。
- 深色主题下的弱文本不能弱到影响可读性。
- 状态颜色不能只靠色相区别，还要保证文字与背景之间的可读对比。

### zoom

- 在 125% / 150% 显示缩放下，核心页面结构仍应可用。
- 放大后不应出现主要按钮被挤出可视区域、标题层级丢失、日志区完全压缩等问题。

### 当前基线映射

- `Layout.tsx` 中导航项本身是可聚焦链接，这为 keyboard/focus 提供了基础入口。
- `SettingsPage.tsx` 中已有表单输入、按钮与开关，后续规范必须要求这些控件在深色主题下维持清晰 focus 与 target size。
- 当前仓库已有基础 UI 测试，但尚未覆盖键盘可达性与 focus 质量，这意味着后续实施阶段需要额外补足验证。

### 明确禁止的未来模式

- 禁止把可访问性降级为可选项。
- 禁止只定义颜色风格而不定义键盘与 focus 规则。
- 禁止为了“精致”牺牲最小点击区域与文本可读性。

## 验收标准与验证方法 (Verification)

本规范的验收分为两层：**Spec completeness** 与 **Code adoption verification**。

### Spec completeness

Acceptance criteria for the specification itself are listed in this section and the following code adoption section.

用于判断“规范文档本身是否完整、明确、可执行”。

必须满足：

- 文档必须包含完整章节：适用范围、非目标、视觉基线、交互基线、Token 架构、卡片层级、主操作规则、状态反馈矩阵、页面模板、组件规范、桌面端约束、可访问性要求、验收与迁移说明。
- 文档中不得存在核心决策未完成的残留表述，例如“待定”“后补”“以后再决定”。
- 文档中的规则必须以 must / must not / required 等硬约束语言表达，而不是主观描述。

### Code adoption verification

Acceptance criteria for implementation adoption are listed below.

用于判断未来代码是否真正按规范落地。

最小验证方式包括：

- `npm run build`
- `npm test`
- 结构检查：关键页面和组件是否符合规范要求
- 文档与代码映射检查：是否仍可从现有页面/组件中追溯规则落点

### 推荐验证工具

- **Bash**：运行 `npm run build`、`npm test`、文档结构检查命令
- **Read**：核对规范文本是否包含必须章节与必须规则
- **Grep / 搜索**：检查是否仍残留与规范冲突的模式
- **页面测试**：用于验证结构和交互基线未被破坏

### 可执行验收要求

#### 文档层
- 文档必须存在唯一正式路径：`docs/ui/desktop-ui-design-spec.md`
- 文档必须能通过章节关键词检查
- 文档不得包含主观验收措辞，例如纯审美主观判断或无法执行的目测结论

#### 代码层
- 构建命令必须成功
- 测试命令必须成功
- 若后续落地涉及页面结构调整，必须补充相应页面/组件测试

### 明确禁止的验收方式

- 禁止把纯审美偏好作为唯一验收条件。
- 禁止把仅能编译通过视为 UI 规范落地完成的充分条件。
- 禁止用无法执行的抽象描述代替具体命令与断言。

## 差距分析

以下差距分析用于描述**当前实现**与**目标规范**之间的偏离项，不直接要求立刻进入代码变更，而是为后续渐进式落地提供优先级依据。

### 页面级差距

#### 规则编号 G-01：工具库首页的主次层级仍不够稳定
- 对象：`src/pages/ToolListPage.tsx` + `src/components/ToolCard.tsx`
- 现状：工具库已经采用卡片优先结构，但卡片内信息与动作竞争仍偏多。
- 影响：会削弱“强主次”和“单主操作”规则，影响扫描效率。
- 优先级：High

#### 规则编号 G-02：设置页仍处于“显式保存”过渡形态
- 对象：`src/pages/SettingsPage.tsx`
- 现状：设置页当前仍以“保存设置”为 page-level primary action。
- 影响：与已确认的“即时生效”方向不一致，未来需要收敛即时生效与失败回滚模式。
- 优先级：High

#### 规则编号 G-03：安装向导的日志反馈容易压过主流程
- 对象：`src/pages/InstallWizardPage.tsx` + `src/components/LogViewer.tsx`
- 现状：日志区域视觉存在感较强，承担了大量过程反馈。
- 影响：会冲淡步骤状态、主动作与结论信息的层级。
- 优先级：High

#### 规则编号 G-04：当前页面缺少统一的空状态与错误表达
- 对象：`ToolListPage`、`InstallWizardPage`、`LogViewer`
- 现状：空状态与错误状态已有兜底，但文案语气和呈现层级尚未统一。
- 影响：不同页面的体验一致性不足。
- 优先级：Medium

### 组件级差距

#### 规则编号 G-05：工具卡片的危险动作仍与主动作同区竞争
- 对象：`src/components/ToolCard.tsx`
- 现状：卸载动作虽已降级为危险色，但仍和主动作处于同一操作区。
- 影响：会削弱主动作识别速度。
- 优先级：High

#### 规则编号 G-06：状态标签规则还未在所有场景中形成统一扩展策略
- 对象：`src/components/StatusBadge.tsx`
- 现状：当前状态标签映射清晰，但还没有与未来组件规范和 token 形成强约束联动。
- 影响：后续页面或组件扩展时可能出现颜色/语义漂移。
- 优先级：Medium

#### 规则编号 G-07：日志容器仍偏工程终端样式，需控制其页面层级
- 对象：`src/components/LogViewer.tsx`
- 现状：黑底终端风格清晰，但在现代精致方向下需要更严格限制其视觉优先级。
- 影响：在长任务场景中可能夺走主流程注意力。
- 优先级：Medium

### 规范落地级差距

#### 规则编号 G-08：Token 体系已定义，但尚未映射到实际组件实现
- 对象：规范与当前实现之间
- 现状：文档中已有 primitive / semantic / component token 架构，但生产代码仍主要依赖现有 utility class 直接组合。
- 影响：若不继续在实施阶段约束，token 会停留在文档层。
- 优先级：High

#### 规则编号 G-09：可访问性与桌面端约束目前仍以原则为主，尚未量化
- 对象：规范与未来实现
- 现状：keyboard、focus、zoom、window size、density 等要求已被定义，但没有落到具体阈值。
- 影响：未来落地时可能出现“遵守了原则但结果不一致”的执行偏差。
- 优先级：Medium

### 差距分析总规则

- 差距分析只负责识别偏离项、影响范围和优先级。
- 差距分析不会变成实现说明，也不会要求立刻进入重构阶段。
- 后续实施阶段应优先处理 High，再处理 Medium，Low 可按页面迭代节奏处理。

## 验收与迁移说明 (Migration Plan)

### 规范产出完成的定义

当以下条件全部成立时，可视为“规范产出完成”：

- `docs/ui/desktop-ui-design-spec.md` 已覆盖所有已确认决策
- 文档已形成唯一正式版本，不再依赖草稿理解范围
- 规范中的章节、规则、模板、token、差距分析和验证标准之间没有明显冲突

### 代码落地完成的定义

当未来代码改造满足以下条件时，才可视为“代码落地完成”：

- 对齐后的页面与组件符合本规范的层级、反馈、组件和模板要求
- `npm run build` 成功
- `npm test` 成功
- 结构检查与差距分析中的高优先级问题已被处理或显式说明例外

### 渐进落地顺序

建议按以下顺序推进，而不是一次性全量改造：

1. 工具库首页与工具卡片
2. 安装向导与日志反馈区
3. 设置页与即时生效反馈
4. 通用状态标签、空状态、反馈策略
5. token 与组件命名体系收口

### 迁移原则

- 先对齐高优先级差距，再处理中优先级差距。
- 页面改造优先遵循模板规则，再细化到组件层。
- 组件改造优先消费 token 语义层，不直接新增散落样式值。
- 若存在临时例外，必须在评审中说明其原因、范围和后续回收计划。

### 实施约束

- 不允许以“全局顺手优化”为由扩大改造范围。
- 不允许跳过构建与测试直接宣称与规范对齐。
- 不允许在未建立页面/组件测试的前提下大范围重构关键交互。
